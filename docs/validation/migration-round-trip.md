# Migration round-trip — verified on real PostgreSQL

**Status: EXECUTED and PASSING (2026-10-10).** The `0017` / `0022` reconciliation
is no longer "conceptually sound but untested": it has been run against a real
PostgreSQL 16 server, and the exercise found two real defects — one in `0022`
itself (fixed) and one inherited from the published chain (reported, not
silently patched).

## Environment

| | |
| --- | --- |
| Server | PostgreSQL 16.15 (`postgres:16-alpine` via rootless podman) |
| Migration head under test | `0022_player_summary_defense_actions` (single head) |
| Alembic | `uv run alembic` from `apps/api` |
| Driver env | `DATABASE_URL=postgresql+psycopg://…` (plus the CI's `DB_DSN`, `S3_*`, `SECRETS_KEK`) |

## What was run

1. Fresh database -> `alembic upgrade head`. Result: 12 tables, head `0022`,
   `fight_player_summaries` has `blocks`/`dodges`/`interrupts`, no `blocked`.
2. Fresh database -> `alembic upgrade ea3023c87c0f` (the revision `0022`
   revises, i.e. the representative prior revision).
3. Seed a pre-existing `fights` + `fight_player_summaries` row
   (`total_damage = 99`).
4. `alembic upgrade head`. Result: the pre-existing row keeps
   `total_damage = 99`; the three new counters are `NULL` (no fabricated data).
5. `alembic downgrade -1`. Result: back at `ea3023c87c0f`, all three counters
   gone, the row's data intact.
6. `alembic upgrade head` again. Result: counters restored, row still `99`.

**All checks pass.**

## Defect 1 — `0022`'s downgrade was not a faithful inverse (FIXED)

The first version of `0022` implemented `downgrade()` as
`alter_column(blocks -> blocked)` and left `dodges`/`interrupts` in place. On the
real chain that is wrong: the target revision has *none* of the three columns,
so `alembic downgrade -1` left three columns the target revision does not have.
`migration-test.yml` claims to "verify the migration is reversible" and would
not have caught it, because it only checks exit codes.

`downgrade()` now drops exactly the three counters `upgrade()` is responsible
for. The round-trip above is the regression check.

## Defect 2 — `8b674a6a9cfc` is an autogenerated migration that destroyed columns (REPORTED)

The `0017` / `0022` story in the reconciliation record was reconstructed from
`0017` alone and was wrong. Verified column lifecycle:

1. `0016_player_stats_enrich` adds `damage_taken`, `deaths`, `downs`,
   `stun_breaks`.
2. `0017_player_defense_events` adds `blocked`, `dodges`, `interrupts`.
3. `0018`..`0021` add boon uptimes, `fights.context`, `fight_agents.position_samples`.
4. **`8b674a6a9cfc_phase3_schema_changes` drops all seven of those columns,
   plus `fights.context` and `fight_agents.position_samples`.** It is an
   autogenerated migration (`# ### commands auto generated by Alembic - please
   adjust! ###`) whose model snapshot lagged the live schema, so Alembic
   concluded every recently added column was stale and removed it.
5. `0022` re-adds `blocks`/`dodges`/`interrupts` only.

So `alembic downgrade`ing `0022` can never find a `blocked` column: the
`blocked -> blocks` rename branch in its `upgrade()` is **unreachable on the
linear chain** (kept as harmless defensive code, and now documented as such).

Confirmed at head on the real server:

| column | present at head |
| --- | --- |
| `fight_player_summaries.damage_taken` | no |
| `fight_player_summaries.deaths` | no |
| `fight_player_summaries.downs` | no |
| `fight_player_summaries.stun_breaks` | no |
| `fights.context` | no |
| `fight_agents.position_samples` | no |

Two of the destroyed columns are still advertised by the API:
`apps/api/src/gw2analytics_api/schemas/fight.py` declares `damage_taken: int = 0`
and `stun_breaks: int = 0`, and nothing populates them, because the ORM has no
mapping for either. The API therefore reports a hard zero rather than an
"unavailable" `NULL`.

**Not fixed here, deliberately.** Restoring those columns is a product decision
(are the stats still wanted? should the API fields be removed instead?) and
editing an already-applied migration is not an option. The safe remedy is a new
forward migration, which is left to the reviewer with this evidence. This is
listed as a genuine risk in the handoff report.

## Other limitations

- `alembic downgrade base` is **not supported** by this chain: at least one
  migration's `downgrade()` is unimplemented, so a full rollback fails. Only
  one-step downgrade is exercised (which is all `migration-test.yml` claims).
  The round-trip above works around it by dropping and recreating the database.
- The seeded fixture needed `SET session_replication_role = replica` to insert a
  child row without its parent; the fixture rows are deleted at the end and the
  database is a disposable container.
