# Phase 3 removed-column consumer audit

**Status: EXECUTED (2026-10-10).** Consumer audit of the nine columns dropped by
the autogenerated migration `8b674a6a9cfc_phase3_schema_changes`, replacing an
earlier and incorrect reading of that migration's consequences
(`docs/validation/migration-round-trip.md` previously claimed the API
"advertises" `damage_taken` and `stun_breaks` with "nothing populating them").

The distinction this document exists to make:

> **missing persistence column ≠ missing product value**

A column can be absent from the schema while the value it once held is still
produced for every consumer on every request, derived from the immutable
versioned event blob.

## Method

Repository-wide trace, not a schema-name reading:

- full `git log -S` history for each column name against the ORM file
  (`apps/api/src/gw2analytics_api/models.py` before commit `26cc42f`, and
  `models/fight.py` after), plus `git grep` over the tree as it stood when the
  columns existed (`ebda00c`, the commit that added `0016`–`0020`);
- current write path (`services/player_summaries.py` → `PlayerRepository.upsert_summaries`),
  read path (`routes/fights/player_aggregators.py`, `repositories/player_repository.py`,
  `routes/players.py`), blob path (`routes/fights/blob_loader.py`), the
  backfill CLI (`scripts/backfill_player_summaries.py`) and the frontend
  consumers under `web/src`;
- the migrations themselves (`0016`–`0022`, `8b674a6a9cfc`).

**Reader's note on semantics:** everything below uses "derived on read" for
values computed per request from the event blob, and "persisted" for values
written into `fight_player_summaries` / `fights` / `fight_agents`.

### What "historical writer: none" is based on

`0016` (adds `damage_taken`, `downs`, `deaths`, `stun_breaks`), `0017` (adds
`blocked`, `dodges`, `interrupts`), `0019` (`fights.context`), `0020`
(`fight_agents.position_samples`) all landed in commit `ebda00c`. At that
revision:

- `apps/api/src/gw2analytics_api/models.py` contains **none** of the nine names
  (`git show ebda00c:apps/api/src/gw2analytics_api/models.py` — no match). The
  table was `fight_player_summaries`, written only through the ORM
  (`PlayerRepository.upsert_summaries` / `add_summary`), so an unmapped column
  could not be written at all. There is no raw `INSERT`/`UPDATE` into that table
  anywhere in the tree, then or now.
- `fights.context`: the only occurrence of `classify_fight_context` in the whole
  tree at `2e6ad71` is inside `0019`'s own docstring. No `context_detector`
  module, no `context=` assignment, no reader.
- `fight_agents.position_samples`: at `ebda00c` the name occurs only in
  `0020_agent_position_samples.py`. Nothing wrote or read it; the positions
  endpoint reads `PositionEvent`s from the blob.

So the columns were **empty schema**: added ahead of the model work, never
populated. `8b674a6a9cfc` (autogenerated, model snapshot lagging the live
database) then concluded they were stale and dropped them — and dropped four
columns that *were* about to become the persistence for features that shipped
later, which is why the migration is a defect and not a cleanup.

**Data loss: none in fact.** No row ever carried a value in those columns. This
does not excuse the migration — it destroyed deliberate schema and would have
destroyed any data written by a deployment that had landed the model work first
(nothing in the published chain guards against that) — but it does mean no
product figure was lost, and none is missing today.

## Split-brain check: `dodges` / `blocks` / `interrupts`

These exist twice on purpose. Both are derived from the same event classes and
the same actor-side key, so the semantics are equivalent; only the audience and
the cache lifetime differ.

| | persisted path | derived-on-read path |
| --- | --- | --- |
| code | `services/player_summaries.py::_process_events_to_buckets` (`DodgeEvent`/`BlockEvent`/`InterruptEvent` → `bucket.dodges/blocks/interrupts`) | `libs/gw2_analytics/player_defense.py::PlayerDefenseAggregator` (`Counter(ev.source_agent_id)`) |
| key | source agent → account | source agent |
| stored in | `fight_player_summaries` (added by `0022`, mapped by `OrmFightPlayerSummary`) | request-scoped, never stored |
| consumers | `GET /players`, `GET /players/{account}`, per-fight history — SQL aggregate over every fight, where re-deriving from thousands of blobs is not an option | `GET /fights/{id}/readout` — single fight, blob already loaded for the other tables |
| gap for pre-`0022` rows | `NULL` → repositories read `or 0`; `scripts/backfill_player_summaries.py` re-derives from the blob for rows where the trio is `NULL` | n/a |

They are not competing values: the readout never reads the summary row for
these counters (it reads it only for boon uptimes), and the roll-up endpoints
never load a blob. Equivalence is pinned by
`apps/api/tests/routes/test_persist_player_summaries.py::test_persisted_defense_counters_match_readout_derivation`,
which runs both derivations over one synthetic event stream and asserts equal
counts.

## `fights.context`

Never written, never read, never exposed: `FightOut` has no `context` field and
no UI surface references one. Restoring the column would persist a value nothing
would produce. If a fight-classification feature is wanted later, it is a new
feature with a new migration, not a restoration.

## `fight_agents.position_samples`

Superseded, not lost. Positions are served from the blob by
`aggregate_player_positions` (`PositionEvent` → downsample 1 per 500 ms, 2000
samples per player), consumed by `GET /fights/{id}/positions`, the readout's
`dist_to_commander`, and the web position/heatmap surfaces. Persisting a second
copy would duplicate a derived artefact whose blob is already the source of
truth, and it would go stale the moment the parser's position handling changes —
which is exactly what the EI migration is expected to change. The
EI field-coverage gate already records positions as an area needing richer
export support (`docs/validation/ei-field-coverage-gate.md`); that gate, not a
restored column, is the place to fix position coverage.

## Verdict

- No forward migration is justified. Three of the nine (`blocked` → `blocks`,
  `dodges`, `interrupts`) are already persisted again by `0022` under the
  product's names and written on ingest; the other six are either derived on
  read from the immutable blob (`damage_taken`, `deaths`, `downs`,
  `stun_breaks`, positions) or were never wired at all (`fights.context`).
- Restoring `damage_taken` / `deaths` / `downs` / `stun_breaks` as columns would
  add a second source of truth for values that are already exact per request,
  and would require a backfill for every historical fight — cost with no
  consumer.
- If a future feature needs a cross-fight defensive rollup that cannot be
  derived per request (e.g. `damage_taken` on the players list), that is a new
  product decision with its own forward migration; the mechanism to follow is
  `0022` + `_process_events_to_buckets`, and the consistency test above is the
  guard that keeps both derivations honest.
